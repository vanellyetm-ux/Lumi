# Mattignation Information Engine v1

**Name:** Mattignation (maturation + mitigation)  
**Status:** proposal / implementation foundation  
**Purpose:** Turn incoming information into traceable, progressively validated knowledge while continuously detecting, containing, and correcting quality, safety, privacy, and operational risks.

## Core idea

Mattignation is a single lifecycle with two inseparable directions:

- **Maturation:** intake → normalize → classify → enrich → corroborate → validate → publish as appropriately qualified knowledge.
- **Mitigation:** detect uncertainty, contradiction, staleness, missing provenance, privacy exposure, harmful inference, and unsafe downstream use; contain, annotate, quarantine, correct, or retire affected claims.

Mitigation is not a final cleanup step. It runs at intake, during every transformation, at publication, and during later re-evaluation. Maturation never erases uncertainty; mitigation never destroys source history.

## Information record

Every item should preserve:
- stable record ID and schema version;
- raw-source reference or immutable source digest;
- source type, author/actor where appropriate, and acquisition time;
- observed-at, received-at, and last-verified timestamps;
- transformation lineage and tool/version identifiers;
- claim-level evidence and citations/references;
- confidence as an explicitly defined assessment, not a probability unless calibrated;
- status and reason codes;
- privacy classification, retention rule, and access scope;
- review, correction, and supersession links.

Never store credentials, access tokens, private keys, or unnecessary sensitive personal data in information records or audit logs.

## Lifecycle

`RECEIVED → NORMALIZED → CLASSIFIED → ENRICHED → CORROBORATED → VALIDATED → PUBLISHED`

At any state, mitigation may transition a record to `FLAGGED`, `QUARANTINED`, `CORRECTION_REQUIRED`, `SUPERSEDED`, or `RETIRED`. A blocked or quarantined record is not eligible for trusted publication.

## Claim-level evidence classes

1. `OBSERVED`: directly measured or directly retrieved evidence with source and time.
2. `REPRODUCED`: independently repeatable result with method and environment.
3. `CORROBORATED`: supported by multiple sufficiently independent sources.
4. `INFERRED`: derived from stated evidence and method.
5. `HYPOTHESIS`: plausible but not established.
6. `SIMULATED`: generated by a model or fixture; never represented as physical observation.
7. `UNKNOWN`: insufficient evidence or unresolvable provenance.

A source count alone does not establish independence. Contradictory evidence must remain visible.

## Mitigation controls

- **Provenance gaps:** quarantine or mark unverified; do not fabricate lineage.
- **Contradictions:** preserve competing claims, identify the exact conflict, request adjudication, and avoid silently choosing one.
- **Staleness:** apply domain-specific freshness windows and surface the last verification time.
- **Uncertainty:** expose unknowns, assumptions, and confidence rationale.
- **Privacy:** minimize, redact, restrict access, and apply retention controls.
- **Unsafe downstream use:** deny use outside declared purpose or authorization scope.
- **Corrections:** append a new version linked to the superseded claim; preserve the prior record and reason.
- **Model drift:** re-evaluate when source, model, schema, or context changes.

## Governance boundary

The engine may classify, validate, compare, flag, quarantine, and prepare reports or remediation proposals. It must not autonomously overwrite or delete source material, read secrets, change permissions, deploy, dispatch external messages, move funds, or actuate hardware. Such actions require a separately implemented and explicit human authorization for the exact operation, target, scope, and time window.

A confidence score, passing test, scheduler, webhook, generated symbol, or automated eligibility decision is never authorization. Deny by default when scope, evidence, policy, or approval is missing or ambiguous.

## Shared Lumi ↔ Ash contract

The same schema and event semantics may be implemented in both repositories. Lumi provides the general information lifecycle and API contract. Ash provides governance integration, approval checkpoints, and evidence/audit policy. Cross-repository exchange is read-only by default and must identify source repository, immutable commit, schema version, and content digest. No repository receives implicit write authority over another.

## Minimum acceptance criteria

- [ ] Raw source is preserved or referenced by immutable digest.
- [ ] Claim and evidence classifications are explicit.
- [ ] Simulation cannot be mislabeled as observation.
- [ ] Contradictions and uncertainty remain visible.
- [ ] Stale data is marked and re-verification is tracked.
- [ ] Corrections append a new version and preserve prior lineage.
- [ ] Quarantined records cannot be published as trusted.
- [ ] Sensitive values and credentials are excluded from records/logs.
- [ ] Authorization is scoped, attributable, expiring, revocable, and bound to exact operation digest.
- [ ] Every decision has provenance and an audit event.
- [ ] Human review is required for consequential operations.

## Rollout phases

1. **Foundation:** schema, lifecycle, reason codes, and examples.
2. **Validation:** deterministic validators and synthetic fixtures.
3. **Mitigation:** contradiction/staleness/privacy/quarantine rules.
4. **Governance integration:** approval and append-only audit contract.
5. **Exchange:** read-only cross-repository manifest and digest verification.
6. **Operational adoption:** dashboards, metrics, and policy-specific freshness windows.

This document specifies the design and acceptance criteria. It does not claim the engine is deployed, connected to production data, or operating on physical systems.
